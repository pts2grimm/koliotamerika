# Тестово публикуване в Hostinger

Този пакет е за Node.js приложение (Next.js + Payload), не за качване като WordPress тема. Снимката от hPanel потвърждава екран за Web App с Git импорт и Upload your files. Постоянният диск и командите при deployment все още трябва да се потвърдят в конкретния план.

## Публикуване само за разглеждане — без постоянна база

За първия визуален преглед добавете **`PREVIEW_MODE=true`** в Hostinger преди Deploy. Оставете Next.js preset, branch `hostinger-preview`, Node 22.x (22.13+) или 24, root `./` и стандартния build `npm run build`.

Не са нужни `DATABASE_URI`, `MEDIA_DIR` или `hosting:prepare` за този режим. При първа заявка приложението само създава временна SQLite база в системната temp директория, прилага включените миграции и импортира публичните страници. Наличен `DATABASE_URI` се игнорира в демото, за да не бъде променена работна база.

Необходими настройки: `PAYLOAD_SECRET` (секрет), `NEXT_PUBLIC_SERVER_URL=https://papayawhip-ram-220810.hostingersite.com`, `SITE_INDEXABLE=false`, `PREVIEW_MODE=true`. За директните реални търгове добавете и `APICAR_API_KEY` (секрет), `AUCTION_PROVIDER=apicar`, `APICAR_VIN_ENABLED=false`. Не копирайте secret placeholder от Codex — въведете реалния ключ отделно в Hostinger.

Демонстрационният режим показва обозначение на всяка страница, изключва формата за запитвания и блокира всички публични API/admin маршрути и HTTP записи, включително първоначална регистрация на администратор. Принудително връща noindex, robots Disallow и празен sitemap дори при погрешно `SITE_INDEXABLE=true`. Публичният frontend, статии, калкулатор и търгове могат да се разглеждат; CRM и админ редакциите не се използват в демото. Данните се възстановяват от публичната снимка при нов процес. Това не замества бъдещото постоянно съхранение.

Проверка в cloud средата: `PREVIEW_MODE=true NEXT_DIST_DIR=.next-preview npm run build`, след това `node scripts/check-preview.mjs`. Проверява два отделни старта, публично съдържание, неактивна форма, блокирани записи/админ, noindex и недокосната постоянна база. Hostinger runtime се проверява отделно след Deploy.

## Пълна версия с CRM и админ — след потвърден постоянен диск

За пълната версия `PREVIEW_MODE` трябва да е `false` или да липсва, след като бъдат изпълнени следващите стъпки.

1. След качване на кода в GitHub изберете **Connect with GitHub**, разрешете достъп до `pts2grimm/koliotamerika` и изберете branch `hostinger-preview`. `package.json` е в корена на репозитория. Алтернатива при работещо изтегляне: **Upload your files → Continue** и ZIP пакетът.
2. На следващия екран проверете автоматично открития **Next.js**, Node **24** (или 22.13+), package manager **npm**, build `npm run build` и start `npm start`. Ако има поле за инсталиране, използвайте `npm ci --include=dev` — TypeScript и подготовката на базата изискват devDependencies.
3. Изберете временен адрес на Hostinger или отделен тестов поддомейн. Адресът за preview не е определен от този пакет.
4. Преди първо стартиране конфигурирайте променливите по-долу, подгответе базата и ограничете публичния достъп, докато собственикът създаде първия администратор.

## Променливи в Hostinger

| Име | Настройка |
| --- | --- |
| `PAYLOAD_SECRET` | Собствен постоянен случаен секрет, поне 32 символа; само в защитените настройки |
| `APICAR_API_KEY` | Ключът за ApiCar, въведен отделно в Hostinger; secret от Codex не се прехвърля със ZIP |
| `AUCTION_PROVIDER` | `apicar` |
| `APICAR_VIN_ENABLED` | `false` — текущият достъп връща 403 |
| `NEXT_PUBLIC_SERVER_URL` | Точният тестов HTTPS адрес, зададен преди build |
| `SITE_INDEXABLE` | `false` за тестовия сайт |
| `DATABASE_URI` | `file:/…/payload.db` с реален абсолютен път върху постоянен диск |
| `MEDIA_DIR` | Реален абсолютен път върху постоянен диск за качените снимки |

Не използвайте примерните многоточия като реални пътища. Тези директории трябва да се запазват при restart и redeploy; обикновена writable build директория не доказва това. Ако платформата не предоставя постоянен диск, преди deployment са нужни външна база и object storage или друг подходящ runtime. Не разчитайте на SQLite файл, който се заменя с всяко качване.

## Инициализиране на празна постоянна база

След инсталацията и задаването на променливите изпълнете `npm run hosting:prepare` в deployment/release средата, която има достъп до постоянния диск. Скриптът прилага versioned миграциите и добавя липсващите 42 страници/статии. Повторно изпълнение запазва редакциите. Не го стартирайте срещу development база, чиято схема е създадена с автоматичния push.

Build средата може да е отделна от runtime. Ако Hostinger не позволява release/startup команда или shell, първо уточнете това; не премествайте инициализацията в build без гаранция, че той вижда същата постоянна база.

Преди отваряне към посетители създайте първия администратор през `/admin` под ограничен достъп. Архивът няма предварително създаден администратор. След това проверете реални търгове, редакция на страница, качване на снимка и тестово CRM запитване. След restart/redeploy проверете, че тези записи и снимката остават. Имейл известията още изискват доставчик.

## Какво съдържа ZIP

Изходен код, package-lock, миграции, публични изображения и снимка на публичното WordPress съдържание. Изключени са `.env`, API ключове, локалната база, качени потребителски снимки, `node_modules`, build/cache папки и Git metadata. Зависимостите и build се създават на хостинга.

## Клиентски акаунти и постоянна база

Клонът `hostinger-preview` съдържа регистрация/вход, профил `/profil`, запазени автомобили (търгове и собствен каталог), прехвърляне на локалните запазени коли и история на запитванията. Гости също изпращат запитвания; само изпратените с активна клиентска сесия влизат в историята. Имейлът сам по себе си не свързва стари или чужди запитвания. Вътрешните бележки са само за администраторите.

`PREVIEW_MODE=true` запазва демото само за преглед. Не активирайте реални регистрации с временната база: данните се губят при рестарт/Redeploy. Празен `DATABASE_URL` не е решение; правилната променлива за приложението е **DATABASE_URI**.

### Вариант за Hostinger Cloud Node.js: външна SQLite база (Turso)

Сайтът остава в Hostinger. Базата се съхранява отделно, така че Redeploy не я изтрива. Стандартните MySQL данни от hPanel не могат да се използват с текущия SQLite адаптер. Ако Hostinger предоставя потвърден постоянен диск за това приложение, може да остане и локална SQLite база; това трябва да се потвърди преди реални клиенти.

1. Създайте база в [Turso](https://turso.tech/) в подходящ европейски регион. Запазете Database URL (`libsql://…`) и Database Auth Token. Проверете условията, цената и възстановяването от резервно копие на избрания план.
2. В Hostinger → приложението → Environment variables добавете `DATABASE_URI` с този URL и `DATABASE_AUTH_TOKEN` с токена. Съхранявайте токена само в защитените настройки. Не го изпращайте в чат и не го качвайте в Git.
3. Запазете стабилен `PAYLOAD_SECRET` (случаен, поне 32 символа) и точния HTTPS адрес в `NEXT_PUBLIC_SERVER_URL`. `SITE_INDEXABLE=false` остава за тестовия адрес.
4. За първо създаване на администратор задайте `INITIAL_ADMIN_EMAIL` и `INITIAL_ADMIN_PASSWORD` (случайна парола от поне 8 символа). При празна база приложението създава само този администратор. При вече съществуващ администратор тези настройки не сменят паролата му. Не задавайте `ALLOW_ADMIN_SETUP=true` на публичния хостинг.
5. Задайте `PREVIEW_MODE=false` и `CUSTOMER_ACCOUNTS_ENABLED=true`, след което Redeploy. За `libsql://` бази версионираните миграции се изпълняват при стартиране и старото съдържание се импортира идемпотентно. При проблем с базата приложението не преминава тайно към временна база.
6. Влезте в `/admin` с определения администратор. След първото успешно създаване премахнете `INITIAL_ADMIN_EMAIL` и `INITIAL_ADMIN_PASSWORD` от настройките.
7. Направете тестова регистрация, запазете автомобил, изпратете запитване и направете още един Redeploy. Проверете, че входът, автомобилът и запитването са запазени. Проверете и достъпа от друг браузър. Това е необходима проверка на реалния хостинг; локалните тестове не я заместват.

За възстановяване на парола конфигурирайте SMTP от пощенския си доставчик: `SMTP_HOST`, `SMTP_PORT` (обикновено 587 или 465), `SMTP_FROM`, `SMTP_USER`, `SMTP_PASSWORD`. Точните стойности са в настройките на пощата; не ги предполагайте. Без SMTP страницата за възстановяване обяснява, че функцията още не е активна. Потвърждение на имейл при регистрация не е включено в тази версия.

Тази база съхранява профили, запазени автомобили, запитвания и CMS съдържание. Качените през админ панела **файлове** са отделни: за тях е нужен потвърден постоянен `MEDIA_DIR` или отделно файлово хранилище. Не започвайте качване на реална фотобиблиотека върху временния диск на приложението. Снимките от API и изображенията в Git не зависят от този upload диск.

Профилите използват отделна HttpOnly бисквитка `koa-customer` (до 7 дни; Secure при HTTPS). Изходът прекратява текущата сесия и на сървъра; сменена парола прекратява старите сесии. Гостите пазят избраните коли в локалното хранилище на браузъра. Опишете тези данни, сроковете им и реалния доставчик на базата в политиката за поверителност преди публичното стартиране.


## Възстановяване след частична инициализация на Turso

Ако има само `users` и `users_sessions`, но няма `payload_migrations`, схемата не е завършена. Успешен анонимен `GET /api/account` не е проверка на базата: без клиентска бисквитка този маршрут връща отговор, без да инициализира Payload.

Началните миграции вече допускат повторно изпълнение: създават само липсващи таблици/индекси и проверяват колоните преди `ALTER TABLE ... ADD`. Това възстановява прекъснато изпълнение на включената схема, без изтриване на записи или ръчно отбелязване на миграции като завършени. Не преобразува произволна несъвместима схема. При несъвместими колони или дублирани стойности за уникален индекс грешката трябва да се прегледа, а данните да се запазят.

1. Запазете резервно копие/snapshot на Turso преди възстановяването. Не изтривайте съществуващите таблици и не изпълнявайте `migrate:fresh`, `migrate:reset`, `migrate:refresh` или `PAYLOAD_DROP_DATABASE=true`.
2. Използвайте същите `DATABASE_URI`, `DATABASE_AUTH_TOKEN` и `PAYLOAD_SECRET`, с `PREVIEW_MODE=false` и production runtime. Не задавайте `PAYLOAD_MIGRATING=true` в постоянните настройки на Hostinger — това е вътрешен флаг само за CLI подготовката.
3. Публикувайте поправения код и стартирайте една инстанция за първоначалното възстановяване. Production инициализацията прилага миграциите преди създаване на администратор и импорт. За remote бази автоматичният development schema push е изключен.
4. Ако има shell/release команда, `npm run hosting:prepare` изпълнява същия списък миграции изрично и еднократно, след което създава липсващия начален администратор и съдържание. Скриптът отказва `PREVIEW_MODE=true`, за да не подготви погрешно временна база.
5. В runtime логовете потърсете `Migrating:`/`Migrated:`, след това `[bootstrap] Schema ready` и `[bootstrap] Ready.`. Ако липсва последното, вземете първата грешка от същия старт; само HTTP 503 не показва на кой етап е прекъснало.
6. Проверете следните read-only заявки в Turso:

```sql
SELECT name FROM sqlite_master WHERE type = 'table' ORDER BY name;
SELECT name, batch FROM payload_migrations ORDER BY name;
SELECT COUNT(*) FROM users;
SELECT COUNT(*) FROM pages;
```

Очакват се двете миграции `20261010_120440_initial` и `20261010_135337_customer_accounts`, както и таблици за страниците, настройките, клиентите, запазените коли и запитванията. Проверете началната страница, входа в админа и отново след рестарт. Съществуващ администратор, включително паролата и сесиите му, не се заменя от `INITIAL_ADMIN_*`.

Регресионните тестове са в `tests/migrations.test.ts` и се изпълняват с `npm test`. Използват отделни временни SQLite бази и отделни production процеси, без външни ключове. Те проверяват възстановяване на частична схема и повторен старт; не заместват проверката на мрежовата връзка и runtime логовете в Hostinger.
